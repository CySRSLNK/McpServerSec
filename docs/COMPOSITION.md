# 组合安全：为什么单个 MCP Server 安全，合起来却不安全

> 本文把研究问题从一个"检测工具"收缩成一个**可证明的命题**。
> 这是毕业设计里最值钱的部分：有命题、有证明、有反例，才不是"我们做了个系统"。

---

## 1. 问题

三个 MCP Server：

| 服务器 | 能力 | 本地策略 | 单独看 |
|---|---|---|---|
| A `docs` | `read_file` | 只能读 `root:docs` | 合规 |
| B `staging` | `write_file` | 只能写 `root:staging` | 合规 |
| C `egress` | `send_file` | 只能发 `root:staging` 里的文件 | 合规 |

单独运行任何一台，都不会泄露：A 只读不写，B 只写不发，C 只发不读 `docs`。
三台一起跑，一条合法调用序列就能把 `root:docs` 的内容发到网上。

**这不是实现 bug，也不是任何一方违反策略。** 它是组合产生的性质。

---

## 2. 形式化

### 2.1 部署与执行

一个部署 `D = (S₁,…,Sₙ, M, Ctx)`：
- `Sᵢ = (Qᵢ, qᵢ⁰, Actᵢ, →ᵢ)`：服务器 i 的 EFSM，`Actᵢ` 是它的工具调用集合；
- `M`：**共享介质**集合（文件系统目录、共享记忆图、数据库表）；
- `Ctx`：Agent 上下文（带标签的条目集合）。

一次执行 `τ = a₁…a_k` 是动作序列，每个 `a ∈ ⋃ᵢ Actᵢ ∪ {ctx_write, ctx_read, compact}`。
组合语义：`D ⊗ = S₁ ⊗ … ⊗ Sₙ`，异步交错，同步点是 `M` 与 `Ctx` 的读写。

### 2.2 局部策略与局部可靠性

每个服务器有一个**局部策略** `πᵢ ⊆ (Qᵢ × Actᵢ)`，只引用 `Sᵢ` 自己的状态与它观测到的入参。

> **定义 1（局部可靠）**：`Sᵢ` 关于全局不变式 `G` 是局部可靠的，当且仅当
> 任何**只含 `Sᵢ` 动作**、且每步都满足 `πᵢ` 的执行 `τᵢ`，都不违反 `G`。

注意这个定义里的执行只涉及一台服务器——这正是"单独测试"的形式化版本。

### 2.3 全局不变式

> **定义 2（不泄露）**：设 `origin(v)` 为值的来源域，`Egress` 为网络出口。
> `G ≡ ∀τ. ∀v ∈ values(τ). ¬( origin(v) = o ∧ v 到达 Egress )`

即：来自 `o` 的内容永远不得到达网络出口。这是**端到端**性质，跨整个部署。

## 3. 命题 1：组合缺口的存在性

> **命题 1**：若下列三条同时成立：
> 1. **标签不透明**：任一步骤的策略 `πᵢ` 只能观测值的类型与大小，不能观测 `origin(v)`；
> 2. **存在共享介质**：存在 `m ∈ M`，`Sⱼ` 可写、`S_k` 可读（`j ≠ k`）；
> 3. **存在源与汇**：`Sᵢ` 能读取 `o` 的内容，且存在某个 `S_l` 能写入 `Egress`；
>
> 那么存在一条执行 `τ`，它对**每个 `πᵢ` 都合规**，却违反 `G`。

**证明（构造）**。取三步序列：

```
a₁ = Sⱼ.write(m, v)       其中 v 是 Sᵢ 从 o 读到的内容
a₂ = S_k.read(m) → payload
a₃ = S_l.send(payload)
```

逐步验证：
- **a₁**：`πⱼ` 的守卫是 `guardⱼ(qⱼ, v)`。由条件 1，`guardⱼ` 无法区分 `v` 与任意同类型良性值 `v₀`。
  又由局部可靠性，`guardⱼ(qⱼ, v₀) = allow`（否则单独运行时连良性写入都被禁，B 不可用）。
  故 `guardⱼ(qⱼ, v) = allow`。
- **a₂**：`S_k` 从 `m` 读出 `payload`，同理 `guard_k(q_k, payload) = allow`。
- **a₃**：`S_l` 收到 `payload`，同理放行。

三步都合规，而 `origin(v) = o` 且 `v` 到达 `Egress`，违反 `G`。∎

**这个证明的关键只有一句**：局部守卫看不见来源，所以它无法把"来自 docs 的内容"
和"任意良性字符串"区分开。**标签不透明是组合缺口的充分条件。**

### 3.1 为什么 MCP 满足条件 1

- MCP 的工具入参是 JSON Schema 约束的**类型值**，没有 `origin` / `taint` 字段；
- `tools/call` 的 params 里，`_meta` 可以携带自定义字段，但**没有任何服务器被要求读取或校验**；
- 因此从 A 到 B 的值，到 B 眼里就是一个 `string`。条件 1 成立。

条件 2、3 在真实部署里极易满足：共享文件系统、共享 memory 图、共享数据库、
以及 C 能发任意 URL。

**结论：MCP 的组合泄露不是一个需要特定 bug 的攻击，而是当前协议形状的必然结果。**

## 4. 命题 2：充分条件（怎么才能安全）

> **命题 2**：若 (i) 每个值在跨边界时携带**不可伪造**的来源标签；(ii) 每个汇点（egress 写）
> 在执行前校验标签，拒绝敏感载荷；(iii) 标签只允许被有权限的组件降级（declassify）；
> 则 `G` 成立。

**证明（对执行长度归纳）**。不变量：每条 `m ∈ M` 或 `Ctx` 中的值，
其携带标签等于其真实 `origin`。
- 基例：初始为空。
- 归纳：`a` 写入 `v` 时按 (i) 附加标签；(ii) 保证写入敏感值到不可信介质时被拒绝，
  故不变量保持；(iii) 保证标签不会被随意降级。
于是任何到达 `Egress` 的值，其标签等于真实来源；若来源为 `o`，由 (ii) 被拒。∎

**含义**：修复位置不在任何一个服务器内部，而在**跨边界**。
这解释了一个工程上反直觉的现象——每台服务器都通过安全审计，系统整体依然泄露。

## 5. 三条通道

组合泄露可以走三种通道，**同一跳里控制流与数据流可以走不同通道**：

| 通道 | 载体 | 例子 | 协议里有无标签 |
|---|---|---|---|
| 参数边（模式A） | 调用参数 | `read_file` → `send_data(content)` | 无 |
| 上下文边（模式B） | Agent 上下文 | `search` → 注入内容 → 下一跳 | 无 |
| 存储边（模式C） | 共享介质 | `read_file` → `write_file` → `send_file` | 无 |

你的 A/B/C 例子是**参数边传路径 + 存储边传内容**的混合：
```
docs.read_file            → 内容进上下文（模式B 的入口）
staging.write_file(param)  → 内容写进共享目录（模式C 的写端）
egress.send_file()         → 从共享目录读出并外发（模式C 的读端）
```

**这是组合检测必须建模外部存储的原因。** 只建模"调用链"（参数边）会漏掉它。

## 6. 检测：怎么自动找到见证

不用穷举全部执行，只做**模式引导的反例搜索**：

1. 从"源"集合出发（能读 `o` 的动作）；
2. 沿三类边做宽度优先扩展，状态是 `(各服务器状态, 上下文标签, 共享介质标签)`；
3. 一旦某步的效果触及 `Egress` 且载荷标签为敏感，**回滚路径即为见证**；
4. 用锥化把范围限制在"能触及该介质的服务器"，深度上限 `k`。

原型里这一步是 `chainbreak/check.py::search`，k=6，3 个服务器时探索 43–56 个状态。

**局部检测怎么做**：把 `scope` 限制为单个服务器，用**同一个 `G`** 跑同样的搜索。
每台都返回 0 条 —— 这就是"单独安全"的形式化验证，而不是嘴上说安全。

## 7. 实验设计

| 实验 | 做法 | 期望 |
|---|---|---|
| E1 局部安全 | 3 个 server 各自单独跑，全局不变式 `G` | 全部 0 条 |
| E2 组合不安全 | 三者一起跑 | 1 条，长度 3，通道 A+C |
| E3 移除性 | 去掉任一服务器（三种二元组合） | 全部回到 0 条 |
| E4 修复 | 加跨服务器流策略 | 0 条 |
| E5 消融 | 去掉存储边建模 | E2 漏检（核心论点） |
| E6 规模 | n=3..8，k=3..8 | 状态数与时间曲线 |

E3 尤其重要：它证明"是三者组合导致"，而不是"某一台本来就坏"。
E5 证明"必须建模共享存储"。

## 8. 与已有理论的关系（必读，避免过度声称）

**这里必须诚实，否则答辩会被一句话击穿。**

"局部安全不蕴含全局安全、需要端到端标签"这件事，**不是新发现**：

- Lampson 1973 的 **confinement problem** 就是问这个问题；
- **信息流控制 / DIFC**（Myers & Liskov 1997）用去中心化标签解决它；
- 动态污点分析、capability 系统，都是同一族方案。

所以**不能声称发现"组合会出问题"**。可辩护的贡献在别处：

1. **MCP 的特殊形状**：协议没有标签通道，而**Agent 本身就是 declassifier**——
   它把 A 的输出重写成 B 的参数，标签在这一步必然丢失。这是 MCP 与经典 DIFC 场景的关键差异：
   去中心化标签要求每个组件参与，而 MCP 的中介者是一个语言模型，它没有安全状态。
2. **三条通道的刻画**：参数/上下文/存储，且同一跳可混用。已有工作大多只建模第一条。
3. **可执行的检测与见证**：把上述结论变成能在真实部署上跑出反例的工具，而不是一条设计原则。
4. **测量**：真实 MCP 部署里有多少组合违反流不变式（这才是有分量的实证贡献）。

**建议的表述**：不写"我们发现组合不安全"，写
"我们把 MCP 的组合不安全性归约到标签不透明这一充分条件，并给出可执行的检测方法"。

## 10. 风险与边界

| 风险 | 处理 |
|---|---|
| 命题 1 被视为"重述 Lampson" | 强调 MCP 的 declassifier 是 LLM、协议无标签通道；把贡献放在归约与检测上 |
| 条件 1 可能被"服务器自己加标签"绕过 | 那是条件 (i) 的满足，正说明命题 2 是出路；可作为"设计建议"一节 |
| 局部检测被质疑"范围受限所以必然安全" | 承认这是近似，并在论文里明确：局部检测模拟的是"该服务器的测试套件"，不是它的全部行为 |
| 见证不可在真实服务器回放 | 先只承诺模型内见证，回放作为后续工作 |
