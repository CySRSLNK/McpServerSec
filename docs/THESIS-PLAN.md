## 1. 对原方案的 8 处技术修正

这些不是挑剔，是每一条都会在中期检查时被问到。

### 1.1 EFSM 是模型，不是服务器的运行时组件

原文："每个 MCP Server 有一个持久维护的局部 EFSM"。这句话会被追问："服务器怎么维护？装在服务器里吗？"

正确表述：**EFSM 是你离线构建的、用于推理的抽象工件**。服务器本身不感知它。
更重要的是：MCP 2026-07-28 版已经**删除会话与 `initialize` 握手**，服务器可以完全无状态，
跨调用状态改由"服务器铸造的句柄作为普通参数"传递。所以"持久状态"不是协议给的，
而是你要从**工具语义**（CRUD、游标、句柄、存储）里推出来的。这恰恰是 §3.2 模板库存在的理由。

### 1.2 "上下文"必须形式化定义边界

"同一个 Agent 上下文"是模糊的。至少三种边界，安全含义完全不同：

| 边界 | 定义 | 典型攻击 |
|---|---|---|
| **任务级** | 一次用户请求到最终答复 | 任务内跨服务器污染 |
| **会话级** | 一个对话窗口 | 多轮之间的指令残留 |
| **跨会话/跨客户端** | 共享持久存储（memory、文件、DB） | Five Hops 式的"疫情化"传播 |

**建议**：论文主模型用**任务级**上下文（可判定、状态小），把"跨会话"作为**扩展实验**（一个案例即可）。
不要一开始就做跨客户端，那是另一个课题的量。

### 1.3 事件字母表必须限定

如果事件 = "所有 JSON-RPC 消息"，状态空间立刻爆炸且大部分无关。
建议字母表只保留 6 类：

```
list(server)            发现工具
call(server, tool, args) 工具调用
ret(server, tool, value) 返回
ctx_write(source)       结果进入上下文
ctx_read()              上下文被用于构造下一次调用
auth(server, scope)     授权/凭证获取
```

其余（ping、logging、progress、cancel）**明确声明排除**，写进"假设与限制"。

### 1.4 EFSM 的变量必须有限化

EFSM = FSM + 变量。变量若不限域，模型就不可判定、无法穷举，你的检测器就退化成符号执行器。
解决：**所有变量取有限抽象域**（见 §2.1 的标签格）。例如 `scope` 抽象为
`{none, self, cross, admin}`，`path` 抽象为数据域 `{fs:home, fs:root, net, mem}`。
这是让"模型检测"在毕业设计里可行的**关键工程决定**，务必写进论文方法论。

### 1.5 必须写威胁模型

否则"检测到什么算漏洞"没有依据。建议采用（与 A2ABreak 一致且好辩护）：

> **全合规对手**：服务器遵循 MCP 规范与自身工具契约；客户端是诚实但不完美的；
> 对手的能力来自 (a) 控制一个 MCP 服务器，(b) 向上下文注入内容（工具返回值、资源内容），
> (c) 利用宿主策略的实现缺口。**不假设**任何一方违反协议。

这样你的发现才"不需要任何实现 bug"，这正是这类工作的说服力所在。

### 1.6 状态不一致检测需要额外定义

"状态不一致"这四个字太笼统。建议拆成三个可判定的子类：
- **句柄悬垂**：上下文仍持有句柄，但服务器侧已失效/被替换；
- **信念漂移**：上下文认为"已授权"，但服务器侧 scope 已过期；
- **重复提交**：同一效果在重试/重入下被执行两次。

每一个对应一条可检查的路径条件，比空泛的"状态不一致"好写得多。

### 1.7 精确率必须可度量

只说"检出了 N 个问题"不能答辩。必须准备：
- **正例集**：8 个已知攻击场景（全部自己搭的 testbed 里）；
- **负例集**：20+ 个正常任务轨迹（用于算误报率）；
- **见证回放**：每个报出的问题都能在 testbed 里重放，回放成功率是一个硬指标。

### 1.8 规范版本要钉死

MCP 有 2024-11-05 / 2025-03-26 / 2025-06-18 / 2025-11-25 / 2026-07-28 多个版本，
语义差异很大（尤其会话的存废）。**论文里钉死一个版本 + 一个客户端**，
附录里讨论跨版本差异（这本身就是个不错的"有效性威胁"小节）。

## 2. 核心设计：用一个图统一两种调用模式

这是整篇论文的技术核心，也是你"统一处理两种情况"承诺的兑现方式。

### 2.1 备选：标签格（承载全部四类问题）

数据/权限/敏感度不建具体值，抽象为四元格：

```
L = P × I × S × A
P 来源 (provenance) : {user, srv_i, external, unknown}
I 完整性 (integrity) : {trusted, untrusted}
S 敏感度 (sensitivity): {public, secret}
A 权限域 (authority) : {none, self, cross, admin}
```

格上定义传播规则（论文里给表即可，不需要代码）：
- `read_file`：输出 `(user, trusted, secret, self)`
- `fetch_url`：输出 `(external, untrusted, public, none)`
- `send_data`：要求入参 `S ≠ secret`，否则触发泄漏
- `write_file`：输出沿用入参的 `P` 与 `I`

**"unknown" 这一档是关键**：凡是上下文里没有来源标注的内容（memory 图、压缩后的摘要、
跨会话装载的历史），一律降级为 `(unknown, untrusted, ·, ·)`。这不是保守假设，
而是那类链条成立的充要条件——不这么建模，跨服务器污染根本推不出来。

### 2.2 统一图 G：两种模式 = 两类边

```
G = ( Q, q0, Σ, →, Λ )

Q  = Q_1 × … × Q_n × Q_C          -- n 个服务器 EFSM 状态 × 上下文状态
Λ  : 标签环境（每个数据域 → L 的一个元素）
Σ  = {list, call, ret, ctx_write, ctx_read, auth}
```

`→` 里有三种迁移：

| 迁移类型 | 形式 | 对应 | 含义 |
|---|---|---|---|
| 局部迁移 | `Q_i → Q_i` | 单服务器 | 服务器自身状态变化（句柄、游标、权限） |
| **参数通道** | `Q_i → Q_j`（经 args） | **模式 A 连续调用** | 值以**调用参数**形式直接传下去 |
| **上下文通道** | `Q_i → Q_C → Q_j` | **模式 B 独立调用** | 值先进上下文，再由上下文影响下一次调用 |

**于是"两种模式"变成"同一个乘积图上的两类边"。** 你说的"系统需要统一处理"，在这里是一句话能说清的：

> 模式 A 与模式 B 都是 G 的子图；差别只在数据流走的是参数边还是上下文边，
> 而**安全检测是同一个图上的一条路径可达性问题**。

这个表述可以直接写进论文的"贡献"一节，也是答辩时最容易被认可的一点。
因为多数同类工作只建模了模式 A（调用链），而模式 B（共享上下文）才是 MCP 的真实形态。

### 2.3 为什么这个统一是"对的"而不是"硬凑的"

因为 MCP 协议本身就不区分这两者：服务器只看到"一个请求 + 参数"，
参数是上一跳的返回值还是模型从上下文里拼出来的，协议上没有区别。
两者在协议层是同构的，差别只在**客户端的构造过程**。
所以把差别建模为"边的类型"，而不是"两个系统"，是与协议语义一致的。

## 3. 四层模型的精确化

你的四层（局部 EFSM / 上下文模型 / 事件驱动 / 全局组合）保留，但每层要给出输入、状态、产出。

### 3.1 L1–L2：服务器 EFSM（模板实例化，不做自动学习）

**输入**：`tools/list` 的清单（name、description、inputSchema、outputSchema、annotations）。
**产出**：一个 EFSM `M_i = (Q_i, q_i0, →_i)`，迁移标注效果签名。

关键决策：**不做通用 EFSM 学习，做"原型分类 + 实例化"**。
定义 5 个原型（archetype），覆盖绝大多数真实服务器：

| 原型 | 状态语义 | 实例 |
|---|---|---|
| **无状态工具型** | 单状态 | 计算器、翻译、时间 |
| **资源 CRUD 型** | 资源存在/已读/已改 | filesystem、数据库 |
| **句柄/游标型** | 未铸造 → 已铸造 → 已消费/失效 | memory、分页查询 |
| **授权域型** | 未授权 → 已授权(scope) → 过期 | OAuth 保护的远端 server |
| **存储共享型** | 私有 → 已写入共享 → 已被他方读取 | memory 图、共享 KV |

**做法**：分类可由规则 + LLM 标注 + 人工校准（20 个工具、1 天内可完成）。
效果签名（读域/写域/网络出口/所需授权）由 `annotations` + schema 推断，
并保留"声明 vs 推断"两列——两者不一致**本身就是一类漏洞**（注解谎报）。

**为什么这是正确取舍**：通用学习不可行（你拿不到服务器源码），
而模板库换来的是**可判定性 + 可审计性**，这在方法论上是加分而不是减分。
论文里要明确写："我们以通用性换取可判定性与人工可审计性"。

### 3.2 L3：上下文自动机（你的核心贡献）

**输入**：任务执行过程中的上下文事件。
**产出**：`C = (Q_C, q_C0, →_C)`，状态是**标签集合**，不是文本。

建议的 6 个上下文状态（足够覆盖真实攻击，又足够小）：

| 状态 | 含义 | 为什么需要 |
|---|---|---|
| `C0 clean` | 无不可信内容、无敏感内容 | 基线 |
| `C1 tainted` | 含不可信来源内容 | 模式 B 污染的入口 |
| `C2 secret` | 含敏感内容 | 泄漏链路的一端 |
| `C3 mixed` | 同时含不可信 + 敏感 | **致命三要素的状态**，最有价值的检测点 |
| `C4 compacted` | 上下文被压缩/截断 | **来源标注丢失**，攻击面被严重低估 |
| `C5 restored` | 从持久存储装载 | 跨会话传播 |

迁移：`append(return)`、`inject(user text)`、`read(for prompt)`、
`truncate/compact`、`persist`、`restore`。

其中 **C4 是你的独特观察**：长任务触发上下文压缩后，原始来源信息丢失，
`tainted` 变成 `unknown`，而检测器通常会把它当干净数据。这个点写得好，
比"我们检测了提示注入"高一个层次，且很容易做实验（构造一个长任务让它压缩）。

### 3.3 L4：全局组合

`G = M_1 × … × M_n × C`，边按 §2.2 生成。

**状态空间控制**（必须做，否则跑不动）：
1. **按查询锥化**：只纳入效果域能触及该检测目标的服务器；
2. **k-有界**：深度 ≤ 6（真实链条一般 3–5 跳），迭代加深；
3. **抽象合并**：同效果签名 + 同原型的服务器折叠；
4. **标签抽象**：`Λ` 只保留格上的值，不保留具体字符串。

规模预期：n=4、每服务器 4–10 状态、k=6 时，锥化后单查询 10⁴–10⁵ 状态，秒级。
这个数字要在第 8 周实测确认，**跑不动就调抽象精度，不要调上限**。

## 4. 检测：4 类属性模板 + 见证

### 4.1 四类问题 → 四个可检查模板

| 问题 | 模板（路径条件） | 检查类型 |
|---|---|---|
| **数据污染** | 存在路径：`P=external/untrusted` 的值 → 经参数边或上下文边 → 到达 `I=trusted` 的写入点 | 可达性 |
| **敏感数据传播** | 存在路径：`S=secret` → 到达 `网络出口/外部写`，且中途无 `consent` 事件 | 可达性 |
| **权限混淆** | 存在路径：调用 `j` 时使用的 `A` 与产生该数据的调用的 `A` 不同，且 `A_j ≻ A_i` | 可达性 + 格比较 |
| **状态不一致** | 句柄悬垂 / 信念漂移 / 重复提交（§1.6 三子类），各有独立条件 | 可达性 + 一致性谓词 |

"调用前 / 调用后 / 跨调用"三处检测，对应到实现上是三个阶段：
- **前**：给定当前 `(Q, Λ)`，检查即将发生的 `call` 的前置条件；
- **后**：检查 `ret` 带来的 `Λ` 变化是否让某个不变量失效；
- **跨调用**：在整条路径上检查上述四个模板。

### 4.2 用 EFSM 的 guard 承载"检测"，而不是事后拍脑袋

把安全属性写成迁移的 **guard / 不变式**，两类检查自然出现：
- 把"坏"写成可达状态 → **存在性检查**（找出攻击链）；
- 把"好"写成不变式 → **全称检查**（证明某类链不存在）。

后者是加分项：能说"在我们的模型下，此类链不存在"，比只报问题更有力。

### 4.3 见证 trace 是交付物的核心

每条报告必须包含：
1. 服务器 + 工具 + 参数抽象 + 上下文状态 + 标签变化（逐步）；
2. 该路径上每一步的"合规性"标注（这一步违反了什么？还是完全合规）；
3. **可实例化的具体参数**（至少给出一个能跑通的取值）；
4. 严重性：影响的数据域、是否跨会话、是否需要用户交互。

回放验证（第 13 周做）：用 testbed 里的服务器重放见证，成功率写进实验。
**没有见证的检测结果不要写进论文**，这是答辩最容易被击穿的点。

## 5. 系统架构（模块职责，不含实现）

```
输入层    规范文档 (钉死版本)  +  server 清单  +  客户端策略配置
                    ↓
获取层    spec/      规范 → 合法事件序与义务（人工/半自动）
          manifest/  清单 → 原型分类 + 效果签名 + 声明/推断双列
                    ↓
模型层    model/     IR（JSON）：EFSM、上下文 FSM、标签格
                    ↓
组合层    compose/   乘积构造、两类边生成、锥化、k-有界
                    ↓
检测层    check/     可达性搜索 + 四类模板 + 不变式检查
                    ↓
验证层    verify/    合规性判定、可实例化、回放、严重性
                    ↓
输出层    report/    见证 trace (JSON) + 可读报告 (Markdown)
```

**设计原则**：每层产出可人工审查的工件（IR JSON、见证 JSON、报告）。
毕业设计里"可审查"比"全自动"更能拿分，也更容易写方法论。

| search（mock） | 模式 B 的注入入口（返回带指令的内容） |
| sink（自建） | 外泄终点，便于观测 |
| auth-demo（自建） | 授权域型，演示权限混淆 |
| client ×2 | 一个单客户端，一个双客户端（演示跨会话） |

### 6.2 案例集（8 个）与良性集（20+）

1. 敏感文件读取 → 参数通道外泄（**模式 A 基线**）
2. search 返回注入内容 → 触发高权限写（**模式 B 核心**）
3. 跨服务器同名工具影子（名称覆盖）
4. memory 投毒 → 第二个客户端读取（**跨会话**）
5. 注解谎报（`readOnlyHint=true` 但产生写入）
6. 句柄悬垂：游标失效后仍被使用
7. 上下文压缩后来源丢失（**C4**）
8. 权限混淆：低 scope 数据被高 scope 调用消费
+ 20 个良性任务（正常读写、正常搜索、正常多服务器协作）→ 算误报率

### 6.3 指标

| 指标 | 定义 | 及格线 |
|---|---|---|
| 检出率 | 8 个案例中报出的 | ≥ 6/8 |
| 误报率 | 20 个良性任务中被误报的 | ≤ 2/20 |
| 见证可回放率 | 报出的问题能重放的 | ≥ 80% |
| 检测开销 | 每个任务的搜索状态数 / 时间 | 秒级，状态数 < 10⁵ |
| 覆盖 | 四类问题各至少 1 个案例 | 全覆盖 |

### 6.4 基线与消融（这部分决定论文档次）

**基线**
- B1：只建单服务器模型（无上下文）→ 证明模式 B 必须靠上下文模型；
- B2：规则/正则扫描（工具名 + 危险关键词）→ 证明形式化的必要性；
- B3：零样本 LLM 直接判清单 → 最有说服力的对照（A2ABreak 的零样本基线产出 0 条确认发现）。

**消融**
- 去掉来源标签（一律 trusted）→ 跨服务器链应大量消失；
- 去掉上下文通道边（只留模式 A）→ 案例 2/4/7 应漏检；
- 去掉压缩状态 C4 → 案例 7 应漏检；
- k 从 3 到 8 → 检出率与开销曲线。

**这四组消融恰好能证明你的核心主张**："两种模式必须统一建模，且来源标签是必需品"。
这比"我们做了一个系统"有说服力得多。

## 8. 风险与降级预案

| 风险 | 概率 | 影响 | 降级预案 |
|---|---|---|---|
| 模式 B 的"上下文影响"难以判定（最大风险） | 高 | 核心创新点塌陷 | 降级为**结构化依赖**：只要"不确定来源的内容在上下文中，且随后的调用触及敏感域"即视为候选，由人工复核。论文诚实写明"我们检测的是 may-dependency，不是语义因果" |
| 状态空间爆炸 | 中 | 跑不动 | 锥化 + k 降到 4 + 只保留 3 个服务器；论文报告曲线并讨论 |
| EFSM 原型覆盖不全 | 中 | 某些 server 建不出模型 | 退化为"无状态工具型"，在限制一节说明 |
| 真实服务器行为与模型不符 | 中 | 见证回放失败 | 只对自建 server 承诺回放，官方 server 只承诺模型内见证 |
| 时间不足 | 中 | 做不完 | 砍掉案例 5/6/7，保 1/2/3/4/8；保模式 A+B 的统一性主张 |

**注意降级顺序**：先降"模式 B 的严格性"，再降"服务器数量"，最后才降"案例数量"。
**不要**先砍统一性主张——那是论文的立命之本。

## 10. 创新点（答辩时你要能一口气说完的三条）

1. **统一建模**：把"连续调用"与"共享上下文独立调用"统一为同一乘积图上的**参数边**与**上下文边**，
   而不是两个割裂的模型。这解决了现有工作只覆盖调用链、忽略上下文的问题。
2. **上下文自动机 + 来源标签**：把"上下文"从背景假设提升为一等状态，
   并显式建模**来源标注的丢失**（压缩、跨会话装载），这是跨服务器污染能被自动发现的必要条件。
3. **可审计的模型构建**：用 EFSM 原型库 + 清单实例化替代不可行的"自动学习"，
   以通用性换取可判定性与可解释性，并输出**可回放的见证**。

**不要声称**："我们发现了未知漏洞"。**要声称**："我们提供了可复现、可解释、可回放的检测方法"。
后者守得住，前者守不住。
